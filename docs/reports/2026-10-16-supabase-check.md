# Живая локальная проверка истории Supabase — 16 октября 2026

## Результат

Серверный ключ и таблица доступны. Настоящие операции PostgREST подтверждают
сохранение, чтение, разделение идентификаторов, очистку и отклонение записи по
устаревшей revision. Полный разговор с настоящей моделью локально НЕ прошёл:
Node.js получает HTTP 403 от OpenRouter. Кроме того, сетевые задержки иногда
превышают заданные лимиты Supabase 450/350 мс.

Публикация и деплой не выполнялись. Рабочий код, таймауты, зависимости и .env
агентом не менялись; владелец заменил публичный ключ серверным. Проверялись только
отдельные случайные тестовые пользователи и навык, без чтения чужой истории.

## Условия и проверки

Владелец сообщил о создании проекта, выполнении SQL и сохранении переменных.
Первоначально был указан sb_publishable_ — конфигурация остановила запрос до сети.
После замены на sb_secret_ удалось читать таблицу с полями history, search, revision.

1. Чтение с компьютера: первое соединение заняло 573 мс; три повторных —
   194, 224 и 174 мс. В других попытках установление соединения занимало
   486–744 мс. Лимит чтения 450 мс иногда срабатывал также после успешных чтений.
2. Настоящий локальный обработчик с настоящими Supabase/OpenRouter:
   чтение базы прошло за 368 мс, OpenRouter вернул 403 за 150 мс.
   Обработчик не записал неудачный ответ; проверка нашла пустую историю.
3. Локальный HTTP с настоящей Supabase и фиксированными тестовыми ответами
   вместо модели, на предварительно установленных соединениях:
   - первый обмен записан (POST 201, 175 мс);
   - новый session_id и session.new=true, без state.session, восстановили
     «Барсик» из базы; следующий обмен записан (PATCH 200, 161 мс);
   - отдельное чтение подтвердило четыре сохранённых сообщения;
   - запрос другого пользователя получил таймаут чтения 450 мс и предупреждение,
     поэтому весь сценарий нельзя считать прошедшим;
   - в более ранней попытке запись также получила таймаут 350 мс.
   Полное время запросов с фиксированным ответом — 457 и 454 мс; это НЕ скорость
   настоящей модели. Фиксированный ответ задерживался на 100 мс; соединения
   предварительно устанавливались, чтобы отдельно проверить работу истории.
4. Отдельная проверка контракта реальной базы с диагностическим лимитом 5 секунд
   (код приложения не менялся): INSERT и чтение вернули ту же пару реплик;
   другой идентификатор вернул пустой массив; PATCH очистил history/search и
   поднял revision до 2; PATCH со старой revision=1 вернул пустой массив;
   заключительное чтение подтвердило, что старая история не вернулась.
   INSERT занял 384 мс, очистка — 373 мс: они превышают рабочий лимит записи 350 мс.
   Эта проверка подтверждает логику и доступы, но не прохождение голосового срока.
5. Бесплатный GET /api/v1/key OpenRouter с одним и тем же ключом:
   Node.js — 403 за 135 мс; системный PowerShell-клиент — 200 за 454 мс.
   Ключ работает. Различие сетевого пути/HTTP-клиента установлено, точный механизм
   отказа Node.js не установлен. Не объяснять 403 балансом или неверным ключом.

## Очистка и расходы

Для всех использованных тестовых идентификаторов DELETE получил HTTP 200/204.
После последнего успешного DELETE контрольное чтение завершилось таймаутом:
отдельно подтвердить отсутствие этой записи повторным чтением не удалось.
Чужие записи и схема не изменялись. Локальные серверы закрыты, системный клиент
завершён; оставшихся процессов проверок не обнаружено.

Отправлен один настоящий запрос генерации, получен HTTP 403; успешных настоящих
генераций и поисковых запросов не было. Остальные проверки модели использовали
фиксированные ответы. Фактическое списание по неудачному запросу не проверялось.

## Следующий шаг

Сначала требуется решить проблему локального доступа Node.js к OpenRouter,
после чего повторить ограниченный сквозной сценарий. При текущих локальных
сетевых задержках лимиты Supabase 450/350 мс не обеспечивают стабильность.
Их возможная корректировка должна сохранять общий бюджет 3600 мс; местные замеры
нельзя переносить на Vercel. Проверка Vercel требует отдельного разрешения.

Проверка CRUD не заменяет аудит RLS, проверку всех прав или реальный голосовой
диалог. Настройки Vercel и опубликованная версия в этой задаче не проверялись.

Сквозная проверка опубликованного обработчика с настоящими Supabase и текущей

и навык; каждый запрос имел новый session_id, session.new=true и не содержал
state.session. Поиск в двух коротких вопросах не требовался.

| --- | --- | --- |

Все HTTP-ответы — 200, предупреждений памяти не было. После проверки тестовая
запись удалена: DELETE 204. Это один прогон, а не статистика стабильности; время
включает HTTP-путь от локального клиента, не всю голосовую задержку Алисы.
Отдельные интервалы Supabase на Vercel здесь не измерялись. Код модели,
поиска и лимиты 450/350/3600 мс при публикации не менялись.

Две первоначальные попытки команды очистки из проверочного клиента нельзя
использовать как диагностику навыка: Windows PowerShell принимал и выдавал
кириллицу в cp866, тогда как Node.js передавал UTF-8. Локальный тест без сети
подтвердил искажение. После явной установки UTF-8 только в дочернем проверочном
клиенте сценарий прошёл. Эта правка не затрагивает код приложения. Успешный
сквозной прогон содержит две настоящие генерации без поиска; возможное списание
за предыдущие искажённые команды отдельно не определялось.

Владелец также передал пример ошибочного ответа «20 гонщиков — по два от каждой
из 11 команд». Это проблема качества ответа; сам скриншот не подтверждает,
использовался ли поиск. В опубликованных правилах исходный вопрос без слов
актуальности и фраза «ты не прав» не включают поиск, а год 2026 включает.
Изменение этих правил и выбор другой модели — отдельный следующий этап.
