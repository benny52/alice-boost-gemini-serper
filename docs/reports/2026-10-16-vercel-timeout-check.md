# Проверка Vercel после изменения таймаутов — 16 октября 2026

## Размещение

По команде владельца `main` обновлён до `6b785f07a67c798326f601b0e961d7ac5b3823ee`. GitHub сообщил успешный статус Vercel и создал размещение в окружении Production. Проверен постоянный адрес `/api` тестового проекта с существующим секретом доступа. Секрет не включён в отчёт.

Код до публикации прошёл 30 автоматических тестов. Живые проверки ниже выполнялись отдельно: четыре обращения к Gemini, из них два с предварительным поиском Serper, плюс запуск навыка без внешних API. Состояние между запросами не передавалось; память в этой проверке не исследовалась.

## Вывод и границы

Новая версия размещена. В двух поисковых случаях преждевременной отмены Serper больше не было, однако ни одна из четырёх попыток получить содержательный ответ не дала нужного результата. Увеличение времени поиска само по себе не решило задачу стабильных ответов.

Следующая диагностика — причины ошибок и задержек Gemini, затем качество поисковой выдачи для ближайших событий. Другие модели, автоматические повторы, фоновая обработка и внешнее хранилище в рамках этого размещения не добавлялись. Новые изменения требуют отдельного согласования; тестирование на устройстве Алисы не выполнялось.

## Дополнительная диагностика Gemini

Скриншот журналов, предоставленный владельцем, подтверждает два `REQUEST_TIMEOUT` и один `GEMINI_REQUEST_FAILED` в проверках на Vercel. Первый код означает отмену запроса нашим обработчиком. Второй означает ошибочный HTTP-ответ Gemini, кроме отдельно обрабатываемых 401/403 и 429. HTTP 200 в строке Vercel относится к ответу навыка Яндексу, а не к успешному вызову Gemini.

Полный доступ к журналам через инструменты не получен: браузерный инструмент не запускается, доступ Vercel API не настроен. Исходный обработчик не записывает точный HTTP-статус внешнего сервиса, поэтому восстановить его для старого запроса по этому скриншоту нельзя.

Выполнены два прямых запроса с компьютера через существующий локальный прокси. Ключ, модель `gemini-3.5-flash-lite` и тело запроса взяты из текущей конфигурации и реального обработчика; только внешний предел ожидания увеличен до 15 секунд для измерения полного ответа. На Vercel настройки не менялись.

| Попытка | Ответ Google | Полное время |
| --- | --- | ---: |
| Первая | HTTP 503, `UNAVAILABLE`; сообщение содержит признак перегрузки | 513 мс |
| Вторая | HTTP 200, правильный результат арифметики, `finishReason: STOP` | 4253 мс |

Успешный запрос использовал 154 входных и 3 выходных токена; `totalTokenCount` — 157. Признаков обрезания ответа по лимиту токенов в нём нет. Смена ключа, платный тариф или увеличение выходного лимита этой проверкой не обоснованы.

Подтверждён временный отказ Google при прямом запросе. Это согласуется с [описанием 503 в документации Google](https://ai.google.dev/gemini-api/docs/api-errors), но не доказывает, что исторический отказ на Vercel имел именно этот HTTP-статус. Локальные 4253 мс включают VPN и не являются измерением времени Gemini из Vercel. Вклад сети, очереди модели и холодного запуска по имеющимся данным не разделён.

Локально подготовлено журналирование статуса и времени каждого внешнего запроса; поля перечислены в [спецификации](../PROJECT_SPEC.md). Пять новых проверок сначала воспроизвели отсутствие диагностики и неточную классификацию обрыва чтения ответа; после изменения проходят все 35 автоматических тестов. После отдельного подтверждения владельца диагностический коммит `71ad950c2bffee1e570b3209387432479ebc62fe` отправлен в main; Vercel сообщил об успешном завершении размещения.

В обоих таймаутах Gemini HTTP-заголовки не получены до отмены; это не HTTP-ошибка Google с известным статусом. Успешный вызов Gemini занял 3069 мс и оставил 331 мс до его предела ожидания.

Эти интервалы измерены внутри функции Vercel и включают обращение Vercel к внешнему API и чтение ответа. Участок от компьютера через VPN до Vercel в них не входит. Данные подтверждают исчерпание времени на внешнем вызове Gemini, но не разделяют задержку сети и время ожидания/обработки у Google. HTTP 503 на Vercel этими событиями не подтверждён.

## Запрос из тестирования Яндекса найден, 09:57 по Москве

Владелец сообщал, что его новые вопросы из тестирования Яндекс Диалогов появляются в Serper, но не видны в открытом журнале Vercel. Фильтр только запросов текущего браузера был выключен, домен и путь вебхука совпадали с постоянным адресом Production. На присланном снимке журнала отображался старый диапазон времени. После включения Live владелец отправил один поисковый вопрос о погоде и предоставил ответ Яндекса, запись Serper и раскрытую запись Vercel для этого запроса. Новых диагностических API-вызовов с компьютера в этот момент не выполнялось.

В Vercel запрос начинается в 09:57:08.59 МСК, направлен на постоянный адрес `/api`, User Agent содержит Yandex. Сервер вернул HTTP 200; в тестировании Яндекса получен содержательный ответ о погоде. Поиск отражён в Serper в 09:57:09, расход — один кредит. Значения погоды и актуальность источников независимо не проверялись.

| Этап | Время | Допустимое ожидание | HTTP-статус | Исход |
| --- | ---: | ---: | --- | --- |
| Serper по журналу Vercel | 802 мс | 1500 мс | 200 | ok |
| Gemini по журналу Vercel | 1726 мс | 2588 мс | 200 | ok |
| Выполнение функции Vercel | 2,54 с | — | 200 | Ответ доставлен в тестирование Яндекса |

Serper отдельно показывает 656 мс на своей стороне; это другой интервал измерения, чем 802 мс от начала HTTP-вызова из Vercel до чтения ответа. Сумма двух внешних вызовов — 2528 мс, близка к полной длительности функции. 2,54 с не включают весь путь запроса от интерфейса Яндекса и обратно.

Журнал показывает `Received in London (lhr1)` и `Routed to Washington, D.C. (iad1)`: Лондон — точка входа, Вашингтон — регион выполнения функции. Это соответствует разделению полей в [документации Vercel](https://vercel.com/docs/logs/runtime). Франкфурт, упоминавшийся для прямых тестов через VPN, не доказывает выполнение функции на VPN-сервере владельца. Таймеры внешних вызовов измеряются внутри Vercel.

Итог: наблюдавшееся отсутствие новой записи устранено включением Live; реальный запрос Яндекса прошёл поиск и Gemini на диагностической версии. Этот один успех не отменяет предыдущие таймауты: Gemini ранее не успевал прислать HTTP-статус за 2,6–3,4 с, а здесь завершился за 1,726 с. Причина разброса между сетью и временем обработки Google пока не разделена. Изменение ключей, региона или новый деплой этим тестом не обоснованы.

В запросе Яндекса отсутствует `state.session`. Возвращённая пара сообщений в `session_state.history` подтверждает только формирование состояния, но не его сохранение между репликами; память остаётся отложенной задачей. Работа на физической колонке не проверялась. Код, таймауты и Production при записи этих результатов не менялись.
